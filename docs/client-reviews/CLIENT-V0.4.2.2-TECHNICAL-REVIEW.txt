======================================================================
1. DECISION DE REVISION
======================================================================

Estado general: ACEPTACION PARCIAL, NO APTO TODAVIA PARA MERGE A main.

La entrega mejora correctamente la arquitectura general del cliente, resuelve la
separacion entre Catalogo y Operaciones globales, incorpora un estado compartido,
propone el proxy Vite para /api y presenta Horario efectivo como campos legibles.

Sin embargo, la entrega no completa el flujo funcional de las diez operaciones.
Las acciones SECTION y MEETING_CASE quedan bloqueadas porque academicPeriod no se
adquiere ni puede introducirse, GlobalActionForm no forma parte del parche y no
recibe scope ni sessionNumber, no existen formularios especificos completos y no
se ejecutaron previews contra el backend.

No aplicar este parche directamente sobre main. Integrarlo primero en una rama de
revision y corregir los puntos marcados como NO CUMPLE.

[NO CUMPLE] Adquisicion de academicPeriod

Evidencia recibida:
- Al abrir una fila de la bandeja, src/App.tsx asigna masterSessionId,
  sectionCode y sessionNumber.
- No existe asignacion de academicPeriod.
- OperationsPage exige academicPeriod para SECTION y MEETING_CASE.

Impacto:
- Las dos acciones SECTION permanecen deshabilitadas.
- Las tres acciones MEETING_CASE permanecen deshabilitadas.

Correccion obligatoria:
1. Obtener el detalle real mediante GET
   /api/admin/v1/meeting-cases/{master_session_id}.
2. Normalizar los aliases reales, sin derivaciones arbitrarias:
   - academic_period o periodo_academico
   - section_code o codigo_seccion
   - session_number o sesion
   - master_session_id
3. Guardar el resultado en GlobalOperationSelection.

Referencia funcional:
- docs/client-next-iteration/examples/src/App.integration.example.tsx
- docs/client-next-iteration/examples/src/types/global-operations.example.ts

Ejemplo esperado:

function resolveMeetingCaseTarget(detail: Record<string, unknown>) {
  const academicPeriod =
    detail.academic_period ?? detail.periodo_academico;
  const sectionCode =
    detail.section_code ?? detail.codigo_seccion;
  const sessionNumber =
    detail.session_number ?? detail.sesion;

  if (
    typeof detail.master_session_id !== "string" ||
    typeof academicPeriod !== "string" ||
    typeof sectionCode !== "string" ||
    typeof sessionNumber !== "number"
  ) {
    throw new Error(
      "El expediente no contiene el target academico completo.",
    );
  }

  return {
    masterSessionId: detail.master_session_id,
    academicPeriod,
    sectionCode,
    sessionNumber,
  };
}

[NO CUMPLE] scope no se entrega a GlobalActionForm

Evidencia recibida:
- selection.scope existe.
- OperationsPage llama GlobalActionForm sin prop scope.

Impacto:
- El formulario debe volver a inferir el endpoint por codigo o por presencia de

  MEETING_CASE -> executeMeetingCaseAction
  SECTION      -> executeSectionAction

  PIPELINE     -> executePipelineAction

[NO CUMPLE] sessionNumber no se entrega a GlobalActionForm

- GlobalOperationSelection contiene sessionNumber.
- OperationsPage no pasa sessionNumber al formulario.

Impacto:

Correccion obligatoria:

---------------------------------------------------------------------
[NO CUMPLE] Validacion combinada action.scope + matriz local

Evidencia recibida:
- OperationsPage filtra solamente por ACTIONS_BY_SCOPE[scope].includes(a.code).

Impacto:
- Si el backend informa un scope diferente, el cliente lo ignora.

Correccion obligatoria:

catalog.filter(
  action =>
    action.scope === scope &&
    ACTIONS_BY_SCOPE[scope].includes(action.code),
);

Si existe discrepancia, mostrar una advertencia de contrato y deshabilitar la
accion. No corregir silenciosamente el scope devuelto por el backend.

4. LLAMADA ESPERADA A GLOBALACTIONFORM
======================================================================

La integracion debe pasar todas las propiedades de contexto:

<GlobalActionForm
  action={selection.action}
  scope={selection.scope}
  date={selection.processingDate}
  section={
    selection.academicPeriod && selection.sectionCode
      ? {
          period: selection.academicPeriod,
          code: selection.sectionCode,
        }
      : undefined
  }
  masterSessionId={selection.masterSessionId}
  sessionNumber={selection.sessionNumber}
  adminKey={adminKey}
  operator={operator}
  onCancel={...}
  onCompleted={...}
/>

GlobalActionForm debe definir tipos explicitos para estas propiedades y no debe
inferir scope por heuristicas.

8. CRITERIO DE ACEPTACION
======================================================================

La siguiente entrega podra aprobarse solo si:

1. Las diez acciones aparecen en el renglón correcto.
2. action.scope coincide con la matriz local.
3. DATE y PIPELINE usan processing_date.
4. SECTION permite seleccionar academic_period y section_code.
5. MEETING_CASE obtiene master_session_id, academic_period, section_code y
   session_number desde el expediente real.
6. GlobalActionForm recibe scope y sessionNumber.
7. GlobalActionForm construye payload especifico por accion.
8. Las mutaciones exigen reason y preview previo.
9. Idempotency-Key se conserva durante reintentos de la misma intencion.
10. request_id y process_run_id se mantienen separados.
11. Horario efectivo se muestra mediante campos legibles.
12. No aparece JSON crudo como resumen principal.
13. No existe desplazamiento horizontal causado por contenido tecnico.
14. TypeScript y Vite build terminan con codigo 0.
15. Los previews seguros se ejecutan contra el backend.
16. Ningun archivo protegido es sustituido.
17. Los archivos fuente se entregan formateados.
